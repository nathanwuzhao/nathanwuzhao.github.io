Challenge

VIGIL helps a blind or low-vision user find an object. A scout drone searches the room and locates the object, and the glasses guide the wearer to it. The glasses have to give an unmistakable left/right cue and warn about obstacles while streaming video. All of this runs over an offline 2.4 GHz link that drops packets, and a dropped link must never leave a servo pressed against someone's face.

3rd overall of 268 at HackGT 13.

Architecture

The two boards share an access point but have no wires between them. The ESP32-CAM hosts the AP and serves video. The Nano joins the AP as a station and talks to the laptop directly. An earlier version relayed the Nano's bytes to the laptop through the CAM over UART. That design made servo commands queue behind a task that was also shipping 25 KB JPEG frames, and every protocol change meant opening the glasses to reflash the CAM. Splitting the paths removed both problems: control latency no longer depends on video, and a protocol change is a Nano-only reflash over USB-C.

The laptop uses a second Wi-Fi adapter for the drone's own AP. The two networks are on separate subnets (192.168.4.x and 192.168.10.x), so the OS routes each by interface with no conflict.

Protocol

ASCII lines, one per UDP datagram. Telemetry from the Nano:

T,<seq>,<uptime_ms>,<tof_l_mm>,<tof_r_mm>,<press_l>,<press_r>,<link>
D,<dir>Primary cue: −1 left, 0 none, +1 right. The pad opposite the turn presses, nudging the wearer the right way.
H,<l>,<r>Hold press depth, 0–100 per side.
P,<side>,…Pulse burst for events like "arrived". The Nano generates it as a non-blocking state machine, because timing a rhythm from Python over congested Wi-Fi comes out ragged.
ZRelease both pads immediately.
C,<side>,…Retrim one side's servo angles at runtime, without reflashing.

The host sends absolute setpoints, not increments, and resends them at 20 Hz. A dropped packet costs one stale update instead of desynchronizing pad position, and the resend stream feeds the Nano's watchdog. press_l/press_r report what the hardware actually applied, so the host can confirm its commands arrived.

Safety

Link lossNo command for 600 ms → both pads release to 0%. That's 12× margin over the 20 Hz resend. Losing the link means no guidance, never a pad held against the face.
Bad inputD,0, non-integers, and out-of-range values all release. No cue beats a wrong cue. Only one pad is ever driven at a time.
Travel clampCompile-time maximum press angle per side, so no command value can over-drive a pad.
Servo floor600 µs minimum pulse instead of 500 µs. At 500 µs the SG90 can stall against its end stop and draw ~700 mA.
PowerOne 5 V supply feeds two high-current regulators: one dedicated to the servos, one for the MCUs, ToF sensors, and ESP32-CAM. Two SG90s draw over 1 A together, so their current spikes stay off the logic rail.

Testing

Command parsing, press math, the travel clamp, burst timing, and the failsafe release were tested in a native harness. It runs 26 assertions against the real .ino, compiled with MSVC against Arduino stubs. Sensors, servo PWM, the access point and video stream, and the Nano joining the AP were all verified on hardware.
